## Key Findings

### Hardware Exposure

- The visible instance is an sGPU slice: PyTorch / MACA runtime expose about 15.6GB, while `mx-smi` shows the physical C500 has 64GB HBM2e.
- C500 exposes 104 AP / SM-like units.
- Warp size is 64, so CUDA-style assumptions like warp size 32 are not portable.
- `mx-smi --show-ap-usage` reports `8 dpc x 13 ap`, matching the 104 AP count.
- `mxcc` can compile and run a minimal custom MACA kernel.

### vLLM / vllm_metax

- `vllm_metax` loads automatically on the C500 vLLM image.
- The stack uses MACA flash attention through vLLM's `FLASH_ATTN` backend.
- Non-eager mode enters `VLLM_COMPILE` and CUDAGraph capture.
- Qwen3-0.6B enables prefix caching; LFM2.5 does not in the observed runs.

### KV Cache / Serving Capacity

LFM2.5 reported much higher cache token capacity than Qwen3-0.6B under the same `max_model_len=2048` / `gpu_memory_utilization=0.70` shape:

| Model | KV cache tokens | Max concurrency for 2048-token requests |
| --- | ---: | ---: |
| LFM2.5-1.2B | 217,952 | 314.35x |
| Qwen3-0.6B | 72,832 | 35.56x |

The important interpretation is that serving capacity is not parameter count alone. Runtime state layout, attention architecture, cache planning, and scheduler behavior all matter.

### API Steady-State

For LFM2.5 with prompt around 237 tokens:

- Eager concurrency 16: about 1,076 completion tok/s, p50 latency about 817ms.
- Non-eager concurrency 16: about 2,266 completion tok/s, p50 latency about 359ms.

Non-eager mode substantially improved steady-state throughput and latency in this serving shape.

### Streaming TTFT / TPOT

For LFM2.5 short-prompt streaming:

- Concurrency 1: TTFT p50 about 15.7ms, TPOT p50 about 4.0ms/token.
- Concurrency 16: TTFT p50 about 63.3ms, TPOT p50 about 5.7ms/token.
- Completion throughput scaled from about 234 tok/s to about 2,258 tok/s.

Longer prompts mainly increased TTFT/full latency, separating prefill pressure from decode cost.

### Prefix Cache / Mixed Prompt Workload

For Qwen3-0.6B:

- vLLM config showed `enable_prefix_caching=True`, `block_size=16`, `prefix_caching_hash_algo=sha256`.
- The concurrency-1 run logged `Prefix cache hit rate: 66.7%`.
- Corrected concurrency-8 run:
  - unique-prefix control TTFT p50: about 112ms
  - shared-prefix cached TTFT p50: about 49ms
  - completion throughput improved from about 750 tok/s to about 1,153 tok/s

This supports the practical serving lesson: prompt layout is a systems decision. Reusable context must appear before request-specific text for prefix reuse to be effective.
